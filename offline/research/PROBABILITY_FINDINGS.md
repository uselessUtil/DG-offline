# 機率與掉落調查

整理日期：2026-10-25。S146–S150 保存歷史 2.9.1／DGDB-1 **r4** 調查，對象 APK SHA-256 為 `f4674e69eff390f42519e530193a4cc986267ffe1036f5380c8655bd799febca`。報告檢查實際交付 DLL，使用隔離 Mono 探測與 Unity I/O 替身；不等於 Android 完整戰鬥。本次僅整理報告並靜態核對後續來源，沒有重跑探測。

## 掉落率的單位與已修正問題

`drop_unit_rate` 的分母為 10,000。敵人的外觀稀有度與掉落角色稀有度須分開；五星資料值是 `rare=4`。調查中五星敵人153筆、掉五星角色179筆，聯集257筆；不能用「五星」推定統一掉率。

r4 離線後端使用反向條件 `rate < roll`，且邊界少一格。隔離探測覆蓋10,000個抽樣值（S149、S150）：

| 設定值 | 應有機率 | r4 實際命中 |
| ---: | ---: | ---: |
| 0 | 0% | 9,999／10,000 |
| 1 | 0.01% | 9,998／10,000 |
| 1,000 | 10% | 8,999／10,000 |
| 3,333 | 33.33% | 6,666／10,000 |
| 10,000 | 100% | 0／10,000 |

這是歷史缺陷。[r8 與後續維護說明](../v291/playable/README.md) 已記錄修正；目前 [QuestRewards291.cs](../v291/playable/QuestRewards291.cs) 使用 `roll < min(10000, rate)`，並先拒絕零率、缺敵人或無掉落角色。r4 報告中的反向機率不能套用到 r10／r12。

1.0.6 final 的比較基準使用正向條件及區域倍率，每個戰鬥敵群依順序取首次成功、最多一個角色掉落；不是整關只能掉一個。六種キングエッグ由原版3,000調至22r7的3,333，六種ハイエッグ由3,000調至4,000。這些來源調整也不能推廣為所有五星同率。

## 需要確認契約的行為

- 非固定敵群數量使用右開區間，1,118組的最小／最大不同；探測2～3只得到2。敵人回合偏移也有右開上界。這能證明實作，但尚不能單憑欄位名稱判定原設計應包含最大值。
- 隨機敵人行動 type1 的三選項合成測試得到11／31、10／31、10／31；當時交付的兩張行動表都是順序 type2，沒有證明目前內容受到影響。
- 技能升級、暴擊、戰鬥面板及危險格70／15／15等已查路徑未發現同類反向判定，不能概括成所有亂數都有問題。Boost 在十個位置抽五次可能重複，不等於保證五個不同格。
